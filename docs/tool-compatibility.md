# Tool compatibility

The `skills/` folders follow the [Agent Skills](https://agentskills.io/specification) standard and work in any client that implements it. Beyond that, three integration layers ship here: a Claude Code plugin (`.claude-plugin/`, `agents/`, `commands/`, `.mcp.json`, `hooks/`, `monitors/`, `workflows/`), an OpenCode plugin (`opencode/` — see [opencode-setup.md](opencode-setup.md)), and a Codex plugin (`.codex-plugin/`, `codex/` — see [codex-setup.md](codex-setup.md)). Each tool ignores the others' layers; `skills/`, `agents/review/`, `bin/` and `hooks/` are shared.

## Notes per tool

- **Claude Code**: full feature set. Agents are namespaced `dotnet-episteme-skills:review:<name>`; Synopsis MCP tools appear as `mcp__plugin_dotnet-episteme-skills_synopsis__<tool>`. MCP servers are not auto-respawned after a crash — reconnect with `/mcp`.
- **OpenAI Codex**: full pipeline, verified on codex-cli 0.145.0. `codex plugin marketplace add Metalnib/dotnet-episteme-skills` + `codex plugin add dotnet-episteme-skills@dotnet-episteme-marketplace` installs skills, the Synopsis MCP server, and the `PreToolUse` guard from `.codex-plugin/plugin.json`; `scripts/install-codex.sh` registers the six `review-*` roles, which a plugin cannot carry. Three Codex behaviours the design works around, each measured rather than assumed:
  1. **MCP commands are never variable-expanded, and MCP processes get no plugin environment.** `${CLAUDE_PLUGIN_ROOT}` is stored literally and spawned directly (`MCP startup failed: No such file or directory`), and a plugin-spawned MCP server's environment has no `PLUGIN_ROOT`/`CLAUDE_PLUGIN_ROOT` — only hooks do. So `mcpServers` points at `codex/mcp.json`, which resolves the shared launcher from `$HOME` through a shell and sets `startup_timeout_sec` for the first-run binary download.
  2. **Hooks work unchanged but cannot be scoped to a role.** The hook process does receive `CLAUDE_PLUGIN_ROOT`, and `tool_name` arrives as `Bash` (Codex maps its shell tool to that name), so `hooks/hooks.json` fires as-is. But `PreToolUse` carries no `agent_type` — only `SubagentStart`/`SubagentStop` do — so `git-readonly-guard.sh` exits 0 (no opinion) there, and read-only enforcement moves to each role's `sandbox_mode = "read-only"`.
  3. **Plugins cannot ship roles or slash commands.** The manifest spec accepts `skills`, `mcpServers` and `apps` and *rejects* a `hooks` field; roles live in the `[agents]` table (`config_file`, `description`, plus `agents.default_subagent_model` / `default_subagent_reasoning_effort` / `max_concurrent_threads_per_session`); and `~/.codex/prompts` is not a feature of 0.145.0, so the orchestrator ships as the `dotnet-techne-review-pipeline` skill under `codex/skills/` (a second skills root, so it stays out of Claude Code and OpenCode).
  Details: [codex-setup.md](codex-setup.md).
- **OpenCode**: full review pipeline via `opencode/dotnet-episteme.js`, whose `config` hook registers the skills path, six `review-*` subagents (prompts read from `agents/review/`, so those files stay single-sourced), the `/dotnet-review` command, and the Synopsis MCP server. Skill folders are also consumed unconverted from its native dirs, `.claude/skills`, and `.agents/skills`. Two sharp edges: **never** copy `agents/review/*.md` into an OpenCode agent directory — a comma-string `tools:` key fails the config decode and takes down config resolution for the whole session; and hand-editing `opencode.json(c)` risks the v1/v2 key-mixing trap, where one v2-shaped key in a v1 document silently discards the entire file. Details and verification commands: [opencode-setup.md](opencode-setup.md).
- **pi (badlogic/pi-mono)**: point pi's skills setting at the `skills/` directory. No subagent/delegation primitive; single-context path only.

## The rule for contributors

Never add tool-specific frontmatter keys to any `skills/**/SKILL.md`. Claude-specific behavior belongs in `agents/`, `commands/`, `.mcp.json`, `monitors/`, or `bin/`; OpenCode-specific behavior in `opencode/`; Codex-specific behavior in `.codex-plugin/` and `codex/` (including the Codex-only orchestrator skill under `codex/skills/`, kept out of the shared `skills/` root so the other tools do not see a second review entry point).

Corollary for the review pipeline: `agents/review/*.md` stay Claude-shaped and the OpenCode plugin converts them at load time. Keep their frontmatter to `name`, `description`, and a tool restriction — and prefer `tools:` there, since it is a stricter allowlist than `disallowedTools:`. Do not try to make those files serve both tools directly: `tools:` is fatal to an OpenCode config document, and the dual-compatible alternative would force every reviewer down to a denylist.
